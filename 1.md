# NOTIFICATIONS.md — Delulu Push Notification Redesign

> Companion to AGENTS.md. Scope: **notification system only**. Auth, Firestore/Supabase split, ecosystem isolation, E2EE, and connection lifecycle are unchanged.

---

## 1. Why your current stack can't do this

| Current piece | Problem |
|---|---|
| **Capacitor Local Notifications** | Fires from JS running *inside* the app. If the app process is killed, no JS runs, so nothing fires. This is why it "only works when the app is alive." |
| **SSE (`/api/connections/:id/stream`)** | Requires an open HTTP connection. Android kills background network sockets aggressively (Doze mode, App Standby). Dead app = no SSE = no delivery. |
| **Web Push (VAPID)** | Works, but it's the *browser* push channel (via the Service Worker `push` event). It's the right idea, wrong transport for a Capacitor/native Android app — Android apps should use FCM directly, which is more reliable, battery-efficient, and gives you native notification control (icon, channel, sound, vibration, tap-intent). |
| **Socket.io** | Already mocked — stays mocked. Not part of this redesign. |

This is exactly the problem Instagram/WhatsApp/Discord solved with **FCM (Android) / APNs (iOS)** — a push channel owned by the OS, not the app process.

---

## 2. What to remove / keep / add

**Web Push stays.** It is not being replaced — it's the correct transport for browser/desktop users. The only change is that the **Android app** gets its own, better-suited transport (FCM) alongside it. Instagram, Discord, and Telegram all run exactly this dual-transport setup: Web Push API for the browser tab, FCM/APNs for the native app.

### ❌ Remove (for chat message delivery only, Android app only)
- Capacitor `LocalNotifications` calls for incoming chat messages (`chat.js`). Local Notifications can stay in the codebase for genuinely local things (e.g., "10-day reveal unlocked" reminder computed client-side while app is open), but **never** for messages that originate on the server — that's the one thing that must go, since it silently fails once the app is backgrounded/killed.
- Nothing else. Web Push/VAPID and the Service Worker (`sw.js`) are untouched and keep serving desktop/browser users exactly as today.

### ✅ Keep unchanged
- **Web Push (VAPID) + `sw.js`** — remains the desktop/browser notification channel, no changes.
- SSE for **foreground** real-time delivery on both platforms (it's cheap and instant while the app/tab is open — no reason to replace it).
- Firestore (users/connections) and Supabase (messages) split.
- Auth/session, ecosystem isolation, E2EE, connection ownership checks.
- `CircuitBreaker` pattern in `utils/circuitBreaker.js` — your existing `pushBreaker` keeps wrapping Web Push calls; FCM gets its own breaker instance alongside it (or the same breaker generalized to accept a transport argument — either works).

### ➕ Add
- **Firebase Cloud Messaging (FCM)** — same Firebase project you already use for Firestore, so no new vendor. This becomes the **Android app's** transport only; browser stays on Web Push.
- `@capacitor/push-notifications` plugin in the Android app.
- A `devices` collection/subcollection in Firestore that stores **both** token types, disambiguated by a `platform` field (`"android_fcm"` or `"web_push"`).
- A small **NotificationDispatcher** service in the backend that fans a single event out to whichever transport(s) a user's registered devices use.
- A **presence map** (in-memory, or Redis if you scale beyond one server instance) so the dispatcher knows who's currently connected via SSE, regardless of platform.
- Android **notification channel** setup (sound/vibration/importance) — required on Android 8+.
- Optional, only needed once you're at real scale: a queue (Cloud Tasks or Redis/BullMQ) between "message saved" and "push sent" so the dispatcher never blocks the message-send request.

## 3. Target architecture (Instagram/WhatsApp pattern)

```
                         ┌─────────────────────┐
                         │   Sender's device    │
                         └──────────┬───────────┘
                                    │ POST /api/connections/:id/messages
                                    ▼
                    ┌───────────────────────────────┐
                    │   Express route handler        │
                    │   1. authz + ownership check    │
                    │   2. save message → Supabase    │
                    │   3. call NotificationDispatcher│
                    └───────────────┬────────────────┘
                                    │
                 ┌──────────────────┴───────────────────┐
                 ▼                                        ▼
      Receiver ONLINE (SSE open)              Receiver OFFLINE / BACKGROUND / CLOSED
      ─────────────────────────               ────────────────────────────────
      Push event over existing SSE             Look up receiver's FCM token(s)
      connection (instant, in-app)             in Firestore `devices` subcollection
                                                       │
                                                       ▼
                                          firebase-admin.messaging()
                                          .sendEachForMulticast(...)
                                                       │
                                                       ▼
                                          Google's FCM infrastructure
                                          (delivers even if app is killed,
                                           phone is locked, or Doze is active)
                                                       │
                                                       ▼
                                    Android system → FirebaseMessagingService
                                    (native background service, not your JS)
                                    builds a NotificationCompat with:
                                      - Delulu app icon
                                      - title / body / timestamp
                                      - sound + vibration pattern
                                      - tap-intent → connectionId
                                                       │
                                                       ▼
                                         User taps → app opens directly
                                         to chat.html?connection=<id>
```

## 4. Full message lifecycle, step by step

### Step 1 — User A sends a message
`POST /api/connections/:id/messages` (unchanged route, unchanged authz, unchanged Supabase insert).

### Step 2 — Backend saves it
`messageOps.send()` writes to Supabase exactly as today. Nothing here changes.

### Step 3 — Backend detects receiver state
Maintain a simple in-memory `Map<userId, Set<sseResponseObjects>>` (you likely already have something like this for SSE broadcast — if not, it's a ~10-line addition). This *is* your presence signal:

```js
const isOnline = connectionEmitter.hasActiveStream(receiverId, connectionId);
```

- **Online (SSE open for this connection)** → push the message over SSE only. No FCM call. This avoids a duplicate "ding" while the user is already looking at the chat.
- **Online but on a different screen (app foregrounded, this chat not open)** → push over the per-user SSE stream (`/api/user/stream`) which already drives your toast/badge system, **and** optionally still send a *silent* FCM data message so the OS-level unread count stays accurate — but suppress the system tray banner client-side since the in-app toast already covers it.
- **Offline / backgrounded / app closed (no active SSE at all)** → this is the FCM path.

### Step 4 — Dispatch, branched by platform
The dispatcher fetches all active `devices` docs for the receiver and sends to each transport in parallel — a phone and a desktop tab both get notified independently:

```js
const devices = await getActiveDevices(receiverId);
const fcmDevices = devices.filter(d => d.platform === 'android_fcm');
const webDevices = devices.filter(d => d.platform === 'web_push');

await Promise.all([
  fcmDevices.length && sendFcm(fcmDevices, payload),
  webDevices.length && sendWebPush(webDevices, payload), // your existing web-push send code, unchanged
]);
```

**FCM (Android app) — new:**
```js
await firebaseAdmin.messaging().sendEachForMulticast({
  tokens: fcmDevices.map(d => d.fcm_token),
  data: {
    type: 'chat_message',
    connectionId: String(connectionId),
    senderId: String(senderId),
    messageId: String(messageId),
    createdAt: message.created_at,
  },
  android: {
    priority: 'high',               // wakes the device promptly
    notification: {
      channelId: 'delulu_messages', // must match channel created client-side
      icon: 'ic_stat_delulu',       // white-silhouette notification icon (Android requirement)
      color: '#YOUR_BRAND_COLOR',
      sound: 'default',
      tag: `conn_${connectionId}`,  // collapses/updates same-chat notifications instead of stacking
      clickAction: 'OPEN_CHAT',
    },
  },
});
```

**Web Push (desktop/browser) — unchanged, just now called explicitly per-device from the same dispatcher instead of being the app's only push path.**

**Important — data message, not "notification" message.** Sending it as a *data-only* payload (rather than FCM's built-in `notification` block) means your own `FirebaseMessagingService` code decides how to render it — including when the app is fully killed. This is what gives you the "exact Instagram behavior": custom icon, title, body, timestamp, vibration pattern, and a tap action that deep-links into the specific chat, all while the JS/webview isn't even running.

**Privacy note (you use E2EE):** since the server can't decrypt message content, the FCM payload body should be generic ("New message" / "Someone sent you a message"), not the plaintext. This mirrors WhatsApp/Signal exactly — the notification tells you *something* arrived; opening the app is what decrypts and shows it.

### Step 5 — Receiver taps the notification
`PushNotifications.addListener('pushNotificationActionPerformed', ...)` fires in your Capacitor JS with the `data.connectionId` you attached. Router navigates straight to `chat.html?connection=<id>`, same as a deep link. If the app was cold-started, Capacitor buffers this event until the webview is ready — no polling needed.

## 5. Where device tokens live

Extend Firestore (no schema change to `users` or `connections` — additive only):

```
users/{userId}/devices/{deviceId}
{
  platform: "android_fcm" | "web_push",

  // populated when platform === "android_fcm"
  fcm_token: String | null,

  // populated when platform === "web_push" (your existing VAPID subscription shape)
  web_push_subscription: { endpoint: String, keys: { p256dh: String, auth: String } } | null,

  app_version: String,
  device_model: String,
  created_at: ISO8601,
  last_active_at: ISO8601,
  active: Boolean
}
```

Both platforms live in the same subcollection so the dispatcher can fetch "all of this user's devices" in one query and branch by `platform` when sending — it doesn't need to know or care how many desktop tabs vs. phones a user has.

Subcollection (not an array field on `users`) because:
- Arrays on a single doc get rewritten wholesale and hit Firestore's 1MB doc limit at scale.
- You need to delete/update a single device's token independently (logout on one device shouldn't touch others).
- Firestore lets you query/delete individual device docs directly.

## 6. Token refresh

FCM tokens rotate (app reinstall, cache clear, periodic OS refresh). Capacitor surfaces this natively:

```js
PushNotifications.addListener('registration', async (token) => {
  await fetch('/api/devices/register', {
    method: 'POST',
    body: JSON.stringify({ token: token.value, deviceId, platform: 'android' }),
  });
});
```

Backend `POST /api/devices/register` does an **upsert** keyed by `deviceId` (a stable UUID you generate once and store in Capacitor Preferences/local storage), not by token — so a refreshed token overwrites the old one for the same physical device instead of creating a duplicate row.

Also handle **send-time invalidation**: `sendEachForMulticast` returns per-token results. Any token with `messaging/registration-token-not-registered` or `messaging/invalid-registration-token` gets its Firestore doc deleted immediately. This is how you keep the token table clean without a separate cron job.

---

## 7. Multiple devices per user

Trivial with the subcollection model: fetch all `active: true` device docs for the receiver, pass all their tokens into one `sendEachForMulticast` call. Each device gets its own notification independently; tapping on one doesn't affect the others. If a user logs out on Device B, `DELETE /api/devices/:deviceId` removes just that doc.

---

## 8. Avoiding duplicate notifications

1. **Single source of truth for "online"**: only the in-memory SSE presence map decides whether to skip FCM. Never send both SSE *and* FCM for the same event to the same connection.
2. **`tag` / `collapse_key` per connection**: multiple unread messages in the same chat update one notification (with a count) instead of stacking N separate ones — same behavior as WhatsApp.
3. **Idempotent message IDs**: the `messageId` in the FCM payload lets the client dedupe against `chat-cache.js` (Dexie) if a message somehow arrives via both SSE (briefly reconnected) and a delayed FCM — the second one is a no-op re-render, not a second banner.
4. **Debounce on rapid sends**: if the sender fires 5 messages in 2 seconds, collapse into one FCM call summarizing "3 new messages" rather than 5 pushes — Instagram/WhatsApp both do this server-side.

## 9. Security

- The Firebase Admin SDK service account key lives **server-only** (same trust boundary as your Supabase service-role key already) — never shipped to the client.
- `/api/devices/register` requires an authenticated session; a token can only ever be attached to the logged-in user's own `devices` subcollection.
- Server validates connection ownership (`getConnection(connectionId, userId)`) **before** looking up tokens or dispatching — unchanged rule #2 from AGENTS.md, just also gates the new push path.
- FCM payload carries no plaintext for E2EE chats (see Step 4).
- On logout / "Not Vibing" account deletion flows, delete the corresponding device doc(s) so a stale token can't receive future pushes.

## 10. Backend changes required

| Endpoint | Change |
|---|---|
| `POST /api/devices/register` | **New.** Upserts `users/{userId}/devices/{deviceId}`. |
| `DELETE /api/devices/:deviceId` | **New.** Called on logout. |
| `POST /api/connections/:id/messages` | **Small addition.** After the existing Supabase insert, call `notificationDispatcher.dispatch(receiverId, connectionId, message)`. |
| New module: `services/notificationDispatcher.js` | Wraps presence check + `firebaseAdmin.messaging()` calls, reuses `pushBreaker` from `utils/circuitBreaker.js` (rename/generalize from Web-Push-specific to transport-agnostic if it currently assumes VAPID). |
| `utils/circuitBreaker.js` | No structural change — same breaker pattern, now wrapping FCM calls instead of/in addition to Web Push. |

Everything else in `server.js` / `database.js` is untouched.

## 11. Capacitor integration

```bash
npm install @capacitor/push-notifications
npx cap sync android
```

`shared.js` (app init, once):
```js
import { PushNotifications } from '@capacitor/push-notifications';

await PushNotifications.requestPermissions();
await PushNotifications.register();

PushNotifications.addListener('registration', (token) => { /* Step 6 above */ });
PushNotifications.addListener('pushNotificationActionPerformed', (action) => {
  const connectionId = action.notification.data.connectionId;
  window.location.href = `chat.html?connection=${connectionId}`;
});
```

Android manifest / native side (one-time setup):
- Add `google-services.json` to `android/app/`.
- Create a `NotificationChannel` (`delulu_messages`, `IMPORTANCE_HIGH`) — required for sound + heads-up display on Android 8+.
- Supply a white-silhouette notification icon (`ic_stat_delulu`) per Android's notification icon spec — a full-color launcher icon will render as a plain white square.

## 12. Scaling notes (millions of users)

- `sendEachForMulticast` batches up to 500 tokens per call — for very active broadcast-style sends (rare in a 1-to-1 chat app, more relevant for e.g. "match found" announcements) batch accordingly.
- Decouple send-from-request: once volume grows, move the `notificationDispatcher.dispatch()` call off the request thread into a lightweight queue (Cloud Tasks, or Redis + BullMQ since you already run infra) so a slow FCM round-trip never delays the sender's `POST` response.
- Keep the presence map in Redis instead of a single process's memory once you run more than one server instance (Render horizontal scaling) — otherwise Instance A won't know Instance B has an open SSE connection for a given user, and you'll under- or over-notify.
- `CircuitBreaker` around FCM protects you the same way it already protects Supabase/Brevo: caps concurrency, times out slow calls, fails fast rather than queuing up.

---

## 13. Summary of the pattern (why this matches Instagram/WhatsApp/Discord/Telegram)

All four use the same shape: **OS-level push transport (FCM/APNs) + server-side presence detection + data-only payloads rendered natively + deep-link tap targets + per-device token tables with server-side cleanup.** None of them poll, and none of them rely on JS-triggered local notifications for messages that originate remotely — because none of that code runs once the app is backgrounded or killed. The redesign above gets you that exact shape while touching only the notification layer of your existing system.
